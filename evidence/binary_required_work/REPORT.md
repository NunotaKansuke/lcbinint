# 高価な微分処理の必要性確認と、安全な削減

## 結論と採用差分

幾何探索を丸ごと消すと、値が同じでも微分が誤る実例が見つかった。
追加Gaussian積分の単純な省略・初期パケットへの置換にも不合格例があった。
そこで、productionでは探索・積分・既存の境界修復を残し、厳密計算の同値な内部最適化だけを採用した。

変更は `tangent/fused_geometry_exact.hpp` と `tests/unit/test_core.cpp`。
今回以前からあったtriple・JAX等の未コミット差分は保持した。
積分・微分のメッシュ選択、要求精度、通常の倍精度経路、精度昇格条件は変更していない。
実行時の微分誤差推定・適応処理は導入していない。

最終版の直接積分比較は、通常のルーターで積分に進むbinary 32円盤×U/LD×相対誤差1e-3/1e-4、計128条件。
値のみ・値＋微分の計256経路条件で、値、値誤差推定、微分、収束・使用可能フラグ、評価点数の
16出力すべてが旧版とビット単位で一致した。

## 必要性をどう検証したか

### 幾何探索の全削除

`ablation/` のコピーだけで、全域のclose-pair detectorを空の結果へ置き換える対照実験をした。
探索を行わず完了と仮定する実験用コードであり、その成功フラグは証明として使っていない。
productionへは反映していない。

この対照実装は最初の98有限差分条件、128条件の直接積分、追加前のC++ unit_coreを通った。
通常の試験を通ることだけでは、削除の安全性は判断できなかった。

そこで、過去のnotebook軌道401点を現在の通常ルーターで選別し、自然に積分へ進む47点で比較した。
7点で結果が変わり、index221に明瞭な反例があった。

主レンズ原点で `(x,y,rho,q,s) =
(1.472109923914061,-0.0007450814495855917,.001,100,1.5)`、線形LD=.5、要求相対誤差1e-4。

| 量 | 探索あり（採用版） | 探索を省いた対照 | 独立な値のみ5点差分 |
|---|---:|---:|---:|
| µ | 71.399165339462 | 71.399165339462 | — |
| dµ/dy | -1727.5488616675 | -1807.6509297359 | -1727.5488618400 |
| dµ/drho | 623.8380291478 | 581.3552470017 | 623.8380298505 |

探索を省くと、dyは約4.6%、drhoは約6.8%ずれた。
値・値の誤差推定・収束フラグは同じで、対照実装の微分もfiniteだった。

差分は微分コードを呼ばない値のみ積分をrtol=1e-10で実行し、
5点差分の刻み2e-5、1e-5、5e-6を比較した。全スカラー参照で値収束と外部support完成を確認。
2つの刻み間変化と全3段の値誤差の伝播を加えた不確かさは約.00140で、
従来のオフライン検査基準 `1e-4 + 2e-4*abs(reference)` より十分小さい。
採用版は両方合格、削除対照は基準に対して約232倍・340倍の差だった。

`ablation-notebook.json` と `ablation-independent-fd.json` に全入力・値・微分・フラグ・差分段階を保存。
この入力をunit_coreに追加し、今後同じ削除を検出できるようにした。
追加後の正常版は合格し、全削除対照をリンクした同じテストは微分不一致のreturn 228で失敗した。

### 追加Gaussian積分の省略・再利用

コードを再確認すると、現在のfused-value-mesh経路は最初の値メッシュ上で微分を計算せず、
後段のGaussian replayで計算していた。「既に運んだ微分を再利用できる」という前提は、
現状の実装の記述としては正しくなかった。

以下を実装・検証したが、すべてproductionからは取り除いた。

1. 初期のパケットをそのまま再利用：未計算の微分まで再利用するため不合格。
   計算済みタグを追加する案に進めた。最初の不合格記録も保持。
2. 値と微分を初期の積分点で同時に運ぶ：境界座標の移動や精密な境界処理まで揃えないと不合格。
3. 境界処理を揃えて再利用：保存済み98条件は通ったが、128条件へ広げると一様光源3点で
   旧版との差が出た。独立なスカラー差分でも不一致を確認した。
   例えばcase27のdµ/dqは再利用案8.9234910、差分8.9086470。
4. 一様光源の初期段数を1段増やす：この不一致を解消できなかった。
5. 一様光源を旧経路へ戻してLDだけ再利用：保存済み98条件と新しいLD差分15成分は合格したが、
   同じ128条件の交互計測では微分時間の中央値が約6–9%増えたため不採用。
   後で再利用できないパネルにも初期の微分計算を増やす費用があった。

したがって、追加積分の全削除やこの単純な同時計算への置換を安全・高速な実装として採用する根拠は得られなかった。
将来、別の微分積分式・キャッシュで代替できないという数学的な不可能性を示したわけではない。

## 採用した厳密計算の最適化

### 同じSturm列を安く構築

旧実装は擬除算の各消去ステップで、余りの全係数の巨大整数GCDを取り、共通因子を除いていた。
擬除算のpivotは正なので、この途中の正規化は余りの正の定数倍を取り除くだけである。
正規化を余り全体が完成した後の1回にまとめても、最終的なprimitive多項式と符号は同じ。
次数を落とすための先頭ゼロ除去は各ステップで維持した。

さらに、巨大整数のGCDを独自の剰余ループからBoostの整数GCDへ置き換えた。
32配置、各5回の比較で、全Sturm列の全整数係数が旧版と完全一致。
構築時間のafter/before比の中央値は約0.183（約5.5倍高速）。
これは構築だけの測定であり、全積分が常に5.5倍になるという意味ではない。

`chain-results.json` は正規化のまとめだけ、`chain-gcd-results.json` はGCD置換を含めた比較。
これらは根の絞り込み最適化を含む同じ基準コード上での、構築段階の比較である。

### 一意と証明済みの根の絞り込み

Sturm変化数で区間に根が1個と証明済みで、端点の多項式値が非ゼロ・異符号なら、
その後は元の厳密多項式の符号だけで同じ根を二分できる。
全Sturm列を毎回評価し直す必要はない。

重根で符号が変わらない場合や端点がゼロの場合は、従来のSturm処理を維持。
根の幅の停止条件・最大深さ・厳密なゼロ判定も維持した。
単根、重根、端点根をunit_coreで検査した。

## 最終速度

`adopted-timing.json`：CPU0固定、thread CPU time、4 warmups後12回。
旧版・採用版、値・微分の4経路を回転・反転順で測定。
別ELF namespace・条件/経路ごとの状態を使用し、同じ完全なseedとsupportの準備を双方で計時外にした。
コンパイルや検証計算との同時実行はない。通常の光度曲線APIの時間ではない。

| 条件群 | 旧版で最も遅い微分時間 | 採用版で最も遅い微分時間 |
|---|---:|---:|
| 一様・1e-3 | 130.88 ms | 17.55 ms |
| 一様・1e-4 | 131.15 ms | 17.60 ms |
| LD=.5・1e-3 | 132.43 ms | 18.71 ms |
| LD=.5・1e-4 | 134.11 ms | 19.52 ms |

各群の最大値の比較であり、同一の1点の比とは区別する。
同じcase25・1e-3では、一様92.57→14.14 ms、LD92.63→14.29 ms。
通常の接触点を含む全条件の中央値はほぼ変わらない（微分時間比after/beforeの中央値1.003–1.006）。
この差分は極端に高い厳密探索の固定費を削るもので、全点で微分追加費用30%以下を達成した結果ではない。

LD・1e-4のcase26/30は、旧版と同じ未収束フラグを維持している。
失敗を収束へ変更していない。全出力の一致は精度の新規認定ではなく、旧版の挙動を保ったことの証拠。
