# Triple通常API・広範囲の速度／処理内訳監査

対象は現在のnative static tripleの通常 `LightCurve.magnification()`。本体・設定・要求誤差は変更せず、測定コードと証拠だけを追加した。相対誤差のみ1e-3／1e-4、一様／線形LD(c=0.5)、12軌道×65点。接触に限らず遠方、非接触、接触直前、横断、光源サイズ、質量比、近接・広い配置を含む。全ケースが水平の静的軌道であり、視差・軌道運動や全配置の網羅検証ではない。

## 結果と見つかった改善対象

1. **外側の経路選択だけが主因ではない。** warmのコースティック木判定は概ね数%。一方、像の支持領域・境界イベントの証明は、かすめるケースの値のみで約70%、惑星質量比で約62%、近接配置で約49%のサンプルを占める。これは外側のpoint/hex距離判定とは別の仕事。
2. **非接触・hex主体では求根と追跡が主因。** 約97%が点像計算。排他的なleafサンプルでは `__hypot_finite`/`hypotf32x` 合計約38%、複素除算 `__divdc3` 約16%。通常範囲用の複素絶対値・除算の軽量化が候補。値と微分の双方に効く。計測は重い演算を特定したもので、置換の正確性・速度改善はまだ未検証。
3. **大きい光源のLDでは積分本体が主因。** 値のみ約79%、微分あり約84%。角度トポロジーの継続、shape-gradientのradius評価、複素イベント、LD項の運搬を調べるべきで、Pythonの固定費削減だけでは解決しない。
4. **微分費用はケース依存。** 遠方は小さいが、近接配置1e-3は一様で約70%、LDで約84%増。かすめるLDも約77%増。全体で30%以内になったとは言えない。近接LD微分のleafではquad演算も約18%を占めるが、これはquadが不要であるという証明ではない。
5. **小さなレンズ形状更新には固定費が残る。** far更新では木の再証明が約42%、grazing更新では約28%。warmの数%とは分けて扱う。初回・更新・同一形状反復の全時間を下に記録した。

## 測定条件

Six independent persistent engine processes, CPU0, one thread, serial rotated/reversed requests. 65 uniformly spaced epochs. Constructor+first API call cold; two warmups, four measured warm calls; four geometry-change calls alternating s*(1.0001/1.0002). Thread CPU ms inside worker exclude IPC/imports/serialization. Ordinary default native LightCurve, no backend flag. VBM TripleLightCurve SinglePoly/MultiPoly/NoPoly, Tol=0/RelTol=request, linear LD; Tol=0 disables its corrquad<Tol point shortcut, this is the requested relative-only contract, not VBM defaults. point_base is an intentionally point-only native mode=0 ablation, not an equivalent finite-source competitor or stage timer. No builds, references or profiling concurrent with timing. CPU frequency/external load uncontrolled.

各条件内のエンジン順を回転・反転して比較した。異なる条件・補足scaling・perf間ではCPU周波数や呼出間隔が揃わないため、絶対時間をそのまま足し引きして処理内訳を作っていない。coldは各エンジン1回で、中央値のwarm／更新より揺らぎに弱い。`point_base`はmode=0の**点光源だけにする診断用ablation**であり、有限光源計算の同等な競合手法でも、中心求根だけを正確に分離したタイマーでもない。

### 証明処理で再利用を検討する具体的な箇所

ソース確認では、`PreparedRegularSupport::contact_plan`は前回のイベント候補を渡せる。一方、通常のcaustic-free支持領域が成立した経路は、継続した像の候補を使っていても最後に新しい `regular_support_detail::event_plan(...)` を構築する。grazingの高い証明費用に対応する候補は、**この通常経路にも分割構造とイベント候補を運び、変更された光源で再証明すること**。古い証明をそのまま使う提案ではなく、速くなるかは次の実装・検証課題。

点像ソルバはwarm時もdegree-10の多項式根10個を継続し、物理像の候補へpolishする。hexのガード側には認証された像数が既にあるため、認証された像数と物理像追跡を組み合わせて不要な候補の仕事を減らす余地も検討対象。ただし、像の完全性・重複排除・残差を保つ必要があり、未実装・未検証の案。単純な演算置換と数学的な仕事量削減は区別する。

## 検証と範囲

- 12軌道×4条件×65点×値／微分の **6240 native epoch出力**。収束失敗 0、無効微分フラグ 0、値／微分の経路不一致 0。cold/warm/更新の保存された全呼出しでも非ゼロstatus 0、無効微分フラグ 0。
- 24軌道・LD組の計364点を、VBM SinglePoly／MultiPolyのrelative1e-7・absolute0で別途照合。各組で粗い比較の差が大きい3点と最初／最後の積分点を選択対象に追加した。native両モード×両要求精度で1456値を比較し、要求誤差を超えた比較は 0。2つの厳しいVBM参照間の最大相対差は 1.3e-10。全6240点を厳しい参照で検証したという意味ではない。
- gradient_validは有限／使用可能性のフラグで、今回新たに全微分方向の高精度を認定したものではない。微分専用の誤差要求・refinementは導入していない。
- 遠方・missの非接触ラベルはnativeの全点PS/hexクリアランス認証と、計時外のcausticサンプルによる位置確認に基づく。grazingはサンプル上の最大caustic高さより1.001*rho外側を通る。サンプル曲線そのものを本体の経路判定に使っていない。
- productionのsource／native hashは測定前後で固定。本体・既存テスト・設定は変更していない。性能改善の採用ではなく、改善対象を特定する監査である。

Raw: cases.json, rows/*.json, references.json, profiles/*.data, profiles/*.symbolized.stacks, profile-summary.json, scaling.json, summary.csv, provenance.json. 実行は `audit.py --cases`, `audit.py`, `references.py`, `profiles.py`, `scaling.py` の順。シンボル解決はrelink.log、symbolize.py、profile_summary.py。
