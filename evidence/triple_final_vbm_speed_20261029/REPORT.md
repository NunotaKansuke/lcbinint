# 最終nativeとVBM三方式の同条件速度比較

native commit `e39af1c4`、DSO `863253398bab41c1d9fbc3018282234fbad67ad3ac57ad9d649ea9b32cb5f7df`。VBM 5.5、native binary hashはPROVENANCEに保存。実装の変更はない。

従来の固定8曲線と直近の固定15曲線、計23曲線を新しく測定した。結果を見て曲線を選び直していない。各入力のrtol/LD/epochをそのまま使い、atol=0。CPU0、1 thread、逐次の独立process、方式の実行順を曲線ごとに回転。import/constructor除外、cold1回、warmup2回、測定9回のthread CPU中央値。呼出しとlist出力化を測り、nativeではstatus検査（微分付きでは有限性検査）も時間に含む。外部負荷とCPU周波数は固定していない。

**倍率 = VBMの値計算時間 / nativeの値計算時間。1より大きければnativeが速い。** 下表は、各曲線の倍率を求めてから取った中央値であり、全曲線をまとめた所要時間比とは区別する。

|VBM方式|中央値|採用曲線数 / 23|nativeが速い曲線数|合計時間比|
|---|---:|---:|---:|---:|
|SinglePoly|1.540倍|8|5|265.658倍|
|MultiPoly|2.506倍|13|8|1.132倍|
|NoPoly|2.573倍|12|10|2.444倍|

倍率に採用するには、全epochに既存の採用済み精度参照があり、native値・native微分経路の値・VBM値の全warm出力が要求誤差内であることを必須にした。全epochの参照があるのは16/23曲線。正常終了やnativeとの一致だけでは採用しない。方法ごとに採用集合が異なるため、対象数とcase IDもSUMMARYへ保存した。

|VBM方式|実行失敗/上限|参照誤差超過|全epochの参照不足|
|---|---:|---:|---:|
|SinglePoly|3|8|4|
|MultiPoly|0|3|7|
|NoPoly|4|0|7|

除外分類は、実行失敗、既知の参照点での誤差超過、参照不足の順に優先する。CPU上限はworker全12呼出しの累積60秒であり、1曲線の時間の下限には読み替えない。
